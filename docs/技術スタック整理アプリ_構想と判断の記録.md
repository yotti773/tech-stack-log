# 技術スタック整理アプリ 構想と判断の記録

手順書が「何をやるか」なら、こちらは「**なぜそうしたか**」の記録。
後から自分が読み返したときや、AIエージェントに背景を渡すときに使う。

---

## 1. 経緯

1. WEBアプリで副業的にマネタイズできないかを検討していた
2. 家計簿、人事・勤怠系APIなどを候補に挙げたが、いずれも競合や自分の負担感から見送り
3. 開発中の健康トラッカーと同じ「収集 → 分析」型で、ニッチな対象を探す方針に転換
4. その過程で「エンジニアが自分の技術スタックを整理するアプリ」のアイデアが出た
5. **収益化を一旦切り離し、Next.js + Supabase の学習題材として作ることに決定**
6. 習熟度を入力する形にし、将来的にコミュニティ化する構想を追加
7. フェーズ1（個人の入力）／フェーズ2（コミュニティ）に分割

**重要な転換点は5番。** 「稼ぐため」から「学ぶため」に目的を切り替えたことで、
競合との差別化や収益性の検討が不要になり、意思決定が一気に軽くなった。

## 2. 目的とスコープ

### 目的（優先順）

1. Next.js + Supabase を実務レベルで理解する
2. 自分の技術スタックを実際に棚卸しする
3. （将来）コミュニティとして育つ可能性を試す

### スコープ

| フェーズ | 内容 | 状態 |
|---|---|---|
| 1 | 略歴・習熟度の入力、公開プロフィール | これから着手 |
| 2 | 集計・発見機能（コミュニティ） | 構想のみ |

### やらないこと（現時点）

- 収益化の検討
- 差別化戦略の作り込み
- リアルタイム機能
- 外部API連携（GitHub連携など）

## 3. 決定事項と理由

### 3-1. 技術スタック: Next.js + Supabase

**理由**: 認証つきCRUDが主体のアプリで、この構成の得意領域とほぼ一致する。
バックエンドを別途書かずに済み、学習対象が「RLS・認証・データモデル」に集中する。

**この構成の弱点**: 長時間バッチや重い非同期処理。今回は該当しないため問題にならない。

### 3-2. 勉強目的に振り切る

**理由**: 既存サービスを調べた結果、以下が判明した。

- LAPRAS等 — Web上の公開データから自動生成する転職サービス。自己申告ではない
- StackShare — 企業のスタック共有が主役。個人の習熟度管理ではない
- COCOREPO等 — SES/SIer向けの法人管理ツール。管理者視点

「個人が自分の意思で手入力し、転職に直結しない棚卸しツール」は空いている。
ただしそれは競合がいないというより、**無料で作れて課金されにくい領域だから**でもある。
収益性を狙うと苦しいが、学習目的なら好都合。

### 3-3. フェーズ分割（個人 → コミュニティ）

**理由**: コミュニティ機能は人が集まらないと空になる。
「最初の1人でも価値があるもの」を先に作り、集計や発見機能はデータが溜まってから足す。

**副次的な利点**: フェーズ1だけでも学習目標（RLS・認証・多対多）は全て達成できる。

### 3-4. `technologies` を共有マスタにする ★後戻り困難

**理由**: ユーザーごとの自由入力にすると「React」「react」「React.js」が乱立し、
フェーズ2の集計が成立しなくなる。後から名寄せするのは極めて高コスト。

**この判断だけは、フェーズ2を作らないと決めても維持する。**

### 3-5. 公開/非公開フラグを行ごとに持たせる

**理由**: 「公開されているものは誰でも読める、書き込みは本人だけ」という
二層のRLSポリシーが書けるようになる。学習題材としての価値がここで最大化する。

### 3-6. 習熟度は5段階＋言葉での定義

**理由**: 数値だけだと人によって基準がばらつき、フェーズ2で分布を出しても意味を持たない。
「業務で使った」「人に教えられる」のように言語化しておく。

## 4. 検討して見送ったこと

| 案 | 見送った理由 |
|---|---|
| 家計簿アプリ | マネーフォワード等の競合が強すぎる |
| 人事・勤怠系API | 自分の経験上、この領域を広げるのはしんどい。大資本と競合 |
| AI検索機能 | 業種・地域の絞り込みで足りる（※企業検索アプリでの判断） |
| GitHub連携での自動収集 | LAPRAS等と同じ土俵になる。また学習対象がぶれる |
| 最初からコミュニティ機能 | データが無い状態では空のページしか作れない |

## 7. AI時代における位置づけ

この題材を今やる意味について、以下の整理をした。

**価値が下がったもの**
`@supabase/ssr` の書き方、RLSの構文など、API表面の知識。AIに聞けば数分で出る。

**価値が上がったもの**
RLSは**間違えてもエラーが出ない**種類の機能。ポリシーの書き漏れで他人のデータが
読めていても画面は正常に動く。AIの出力が正しいかを検証できる判断力が要る。

**したがって**

- 定型部分（M0〜M2、M4のCRUD）はAIエージェントに任せて速く抜ける
- M3（RLS）とM4のデータモデル設計は自分の手で悩む
- 丸投げすると一晩で完成し、学習が丸ごと消える

進め方としては、手順書をリポジトリに置き、**1マイルストーンずつ区切って**
Claude Code に依頼するのが現実的。

### M1. ローカルDBとつなぐ（着手・完了: 2026-07-25）

- Docker Desktop + WSL2 のセットアップが前提として必要だったため、M1着手前にユーザーがインストールを実施（手順は手順書「0. 前提と準備」に記録済み）
- `technologies` テーブルを作成し、共有マスタとして誰でも読める設計にした（3-4の方針通り）。ただしテーブル作成直後は `anon` ロールに権限がなく `permission denied` になったため、マイグレーション内で明示的に `grant select` を追加した。RLSはまだ有効にしていない（M3で対応）
- 動作確認用にダミーの技術データ（Next.js / Supabase / TypeScript / Tailwind CSS）を `supabase/seed.sql` に投入。`supabase db reset` のたびに再投入される
- トップページはServer Componentとして書き換え、`@supabase/supabase-js` の素のクライアントで一覧表示。`@supabase/ssr` やCookieベースの認証はM2で導入するため、ここでは使っていない
- pushした直後、本番Vercelのビルドが失敗した（`NEXT_PUBLIC_SUPABASE_URL`等が本番に無く、Supabaseクライアント生成時に例外が発生したため）。本番用Supabaseの用意はM6の範囲なので、env変数が無いときはデータ取得自体をスキップするようコードを直し、ビルドが通ることを確認してから再push
- **M1完了（2026-07-25）**。次はM2（ログイン機能・Cookieベースのセッション管理）

### M2. ログインできるようにする（着手・完了: 2026-07-25）

- AGENTS.mdの警告（このNext.jsは訓練データと違う可能性がある）が実際に効いた回。Next.js 16で`middleware.ts`が`proxy.ts`に名称変更されており、`node_modules/next/dist/docs/`を確認しなければ古い書き方のまま実装してしまうところだった
- ログイン方式はマジックリンクを採用。理由は手順書の推奨通り「学習目的なら最も簡単」なため。パスワード管理やハッシュ化の実装コストを払わずに、Cookieベースのセッション管理という本質（M2の学習目的）に集中できる
- Supabaseクライアントを3分割する設計は`@supabase/ssr`公式パターンをそのまま採用。ブラウザ用・サーバー用・proxy用（旧middleware用）でCookieの読み書き責務が異なるため
- マジックリンクのメールテンプレートを自前の`/auth/confirm`ルートへ向くようカスタマイズした。デフォルトテンプレートのままだとGoTrueの検証エンドポイントに直接飛ばされ、Next.js側でセッションを確立する制御ができないため（SSR構成では必須の変更）
- 本番Supabase未設定（M6まで）という前提はM1から継続。`proxy.ts`にも同様のenv変数ガードを入れ、本番ビルド・本番リクエストの両方で安全に素通りするようにした
- ブラウザを使わず`curl` + Mailpit APIで一通りの動作確認（ログイン・リロード後の維持・ログアウト影響）を行った。UIの見た目までは確認していないため、次回ブラウザで一度目視確認するとよい
- **M2完了（2026-07-25）**。次はM3（RLSを理解する、★最重要・自分の手で悩みながら進める）

### M3. RLSを理解する（着手・完了: 2026-07-25）

- 方針通り、土台（`profiles`テーブル・自動生成トリガー）はAIが用意し、RLSポリシーの作成と「わざと壊して確認する」ステップはユーザー自身が手を動かして行った
- `alter table ... enable row level security`を実行した直後、ポリシーが1件も無い状態で「何も変わらないのでは」という予想が最初に出たが、実際には**ポリシー0件はデフォルトで全拒否**というfail-closedな挙動になっており、これを`set role anon;`での実験で体感した
- SELECT（`using (true)`）・UPDATE（`using (id = auth.uid())`）の2ポリシーを、1行ずつ意味を確認しながら一緒に書いた
- 検証の過程で、Supabase StudioのSQL Editorは文ごとに接続が変わるらしく`set role`/`set request.jwt.claims`によるなりすましが機能しないという制約が判明。代わりにStudio純正の「Impersonate user」機能（Table Editor右上）を使うことで、実際のユーザーとしてRLSが効いた状態を確認できた
- 自分の行は編集可・他人の行は編集不可を確認したのち、UPDATEポリシーを一時的に`using (true)`に緩めて「誰でも編集できてしまう」無防備な状態も実際に見てから、元のポリシーに戻した
- **M3完了（2026-07-25）**。次はM4（書き込みと多対多）。M4のデータモデル設計部分も学習価値が高いため、M3と同様に土台はAIが用意しつつ設計判断はユーザーと相談しながら進める

### M4. 書き込みと多対多（着手・完了: 2026-07-25）

- 着手前にAskUserQuestionで「習熟度(level)のDB表現」を確認し、`smallint + check制約(1〜5)`を選択。意味の定義（言葉）はDB側に持たせず、アプリ側の定数として持つ方針にした。理由: M4のスコープでは別テーブル化するほどの複雑さが無く、シンプルさを優先
- RLSポリシーはM3と同じ進め方（AIがヒントを出し、ユーザーが実際にSQLを書く）を踏襲。今回は「公開されているか、自分のものか」というOR条件のSELECTポリシーと、INSERT専用の`with check`という、M3には無かった新しい概念が登場した
- 「わざと壊して確認する」もユーザー自身がSupabase Studioの2ユーザー分のテストデータで実施。INSERTで他人のprofile_idを詐称できないこと、他人の行のUPDATE/DELETEが静かに0件影響で終わる（エラーにならない）ことを確認した。この「RLS違反はエラーにならず0件になるだけ」という気づきは、7章で触れた「RLSは間違えてもエラーが出ない」という話の実感として良い収穫だった
- CRUD部分（`user_technologies`のServer Actions、`/mytech`ページのUI）は方針通りAIが実装し、`curl`で本物のログインセッションを使って新規技術追加・二重登録の拒否・カテゴリ別表示・他人の行への書き込み拒否まで一通り検証した
- 副次的な発見: `technologies`（共有マスタ）はM1時点でSELECTしか許可していなかったため、「無ければ新規追加」機能のために`insert`権限の追加が必要だった。GRANTとRLSは別レイヤーという教訓が、書き込み機能を作る段階でもう一度効いた形
- **M4完了（2026-07-25）**。次はM5（公開ページ）

### 番外編: デザインの決定（着手・完了: 2026-07-25）

- 画面導線の見直しに続き、「配色に凝るのは学習目的から外れるかもしれないが、それでも再検討したい」という相談があった。作り込みすぎない範囲で、という前提を共有した上で進めた

- ダークモード対応を続けるかどうかも確認し、「常に同じ見た目に統一（ダークモード廃止）」を選択。既存の`dark:`クラスによる二重管理をやめ、実装をシンプルにする方を優先した

- 検証は`curl`だけでは見た目が分からないため、Playwrightでヘッドレスブラウザからスクリーンショットを撮って目視確認する方法に切り替えた。この過程で、テストスクリプト側の`localhost`/`127.0.0.1`混在によるCookie不整合（M2で学んだのと同じ現象）を一瞬「アプリの不具合」と誤認しかけたが、原因を切り分けて誤りだと判断した
- **完了（2026-07-25）**。次はM5（公開ページ）

### 番外編: デザインの再検討（着手・完了: 2026-07-25）

- C案（スタジオダッシュボード風）を実装・デプロイした後、ユーザーから「AIぽさがあるなぁ、フォントかな？」という感想があった。診断の結果、実際の主因はフォントではなく**配色**（暖色クリーム＋テラコッタ/シエナ系アクセント）で、これはAI生成デザインで最も見かける配色パターンの一つだった。デザインスキルのガイダンス自体がこの組み合わせを名指しで注意していたにもかかわらず、C案採用時にはそこに気づけていなかったことを、ごまかさずユーザーに伝えた
- 色相を大きく変えた2案（D: 寒色・明るい紙色＋Fraunces、E: 濃紺チャコール＋アンバー＋Archivo）をモックアップし、システムフォント頼みだったC案への反省から、両案とも見出しにデータURI埋め込みの本物の書体を使った
- ユーザーがD/Eどちらも選ばず、外部記事（note.com）で見た「ASCII端末・レトロCRT効果」という第三の方向性を提案した。記事URLをWebFetchで読もうとしたところ、アカウントの月間利用上限エラーで取得できなかった。これはリトライで直る性質のエラーではないため、素直にその旨を説明した上で、「CRT端末のレトロ演出」自体は広く確立された意匠なので、記事本文を読まずに一般的な特徴（スキャンライン・フォスファーグロー・画面湾曲のビネット・等幅フォント）からモックアップ（F案）を作成する、という代替方針をとった
- F案をユーザーが採用。単一のダークな画面世界にコミットする方向性のため（CRT端末という被写体上、常時ダークであることが自然）、これまで維持していたライト/ダークモード両対応は行わず、C・D・E同様に単一テーマとして実装した
- 習熟度の表現は、丸ドットのままでは被写体（端末画面）にそぐわないため、信号メーター風の縦長ブロック表示に変更した。ラジオボタン+`:checked ~ label`という基盤の仕組みはC案から変えていない

**学び**: 自分が事前に把握していた「AIっぽいデザインの典型パターン」という知識を、C案を実装した時点での自己チェックに活かせていなかった。ガイダンスを知っていることと、実装時に照らし合わせて検証することは別だという教訓が残った。また、外部リンクの取得が（一時的な障害ではなく）アカウント単位の利用上限で失敗した場合は、リトライに固執せず、確立された一般知識で代替できないかをまず検討するとよい

### M5. 公開ページ（着手・完了: 2026-07-25）

- 着手前に、`profiles`のRLS SELECTポリシーが`using (true)`のまま（＝`is_public`を無視して誰でも読める）だったことに気づいた。これは実装ミスというより、M3時点では「プロフィールを外部に公開する」機能自体がまだ存在しなかったため後回しになっていた設計負債で、M5でようやく顕在化した。`user_technologies`と同じOR条件のポリシーに揃えるマイグレーションを追加し、さらにユーザーの希望で「RLSとアプリの両方で守る」多層防御の方針を採った
- 非公開/存在しないusernameへのアクセスは、区別せず一律`notFound()`で404にする方針にした。「存在するが非公開」と「存在しない」を区別して伝えると、非公開ユーザーの存在自体をユーザー名の総当たりで探索できてしまうため
- キャッシュ戦略は当初「時間ベースのISR（`revalidate = 60`）」を選んだが、実装後の検証（`next build && next start` + `curl -i`でCache-Controlヘッダーを確認）で、共通ヘッダーが毎リクエスト`cookies()`を読む設計のせいでアプリ全体（`/u/[username]`を含む）がすでに完全動的レンダリングになっており、`revalidate`の指定が実質無効だと判明した。ここで改めて「ISRを本当に効かせる」か「常に同じヘッダーがあるという一貫性を優先する」かを確認したところ、後者を選んだ。ヘッダーを分離すればISR化はできるが、この規模のアプリではその一貫性を崩してまで得るメリットが小さいという判断
- usernameが`/u/[username]`のURLに直接使われる設計だったにもかかわらず、これまでフォーマットのチェックが一切無かったこともM5着手時に気づいた抜け漏れだった。`^[a-z0-9_-]{3,20}$`という簡易な制約を追加した

**学び**: 「公開する」というM5の機能追加によって、M3時点では問題にならなかった`profiles`のRLSの緩さが初めて実害になった。RLSポリシーは書いた時点で正しくても、後から機能が増えたときに前提が崩れることがあるため、新しい公開経路を作るたびに関連テーブルのポリシーを読み直す価値がある。また、キャッシュ戦略のような技術選定は、実装してみて初めて既存アーキテクチャとの矛盾が分かることがあるので、「選んだ方針が本当に機能しているか」を`curl`等で実地検証する習慣が効いた
