# 技術スタック整理アプリ 構築手順書（フェーズ1）

Next.js + Supabase で、自分の略歴と技術習熟度を登録・公開できるアプリを作る。
学習目的のため、**1マイルストーンにつき新しい概念は1つだけ**という方針で並べている。

- 想定稼働: 週10時間
- 想定期間: 約8週間（M0〜M6）
- ゴール: 公開URLで自分のスタックと略歴が見える状態

---

## 0. 前提と準備

### 用意するもの

| もの | 用途 | 費用 |
|---|---|---|
| Node.js（LTS版） | Next.js の実行 | 無料 |
| Docker Desktop | ローカルSupabaseの起動 | 無料 |
| GitHubアカウント | ソース管理・デプロイ連携 | 無料 |
| Vercelアカウント | ホスティング | 無料（Hobby） |
| Supabaseアカウント | DB・認証 | 無料 |

> **注意**: Vercel Hobby は非商用・個人利用に限定されている。
> リポジトリは「個人アカウント所有」にすること。Git組織所有のリポジトリは Hobby では接続できない。

### Docker Desktop のセットアップ（Windows）

Supabase CLIの `supabase start` は、PostgreSQL・認証サーバー・管理画面などをDockerコンテナとして一括起動する。そのためWindowsでは事前にWSL2とDocker Desktopが要る。

1. WSL2をインストール（管理者権限のPowerShellで）
   ```
   wsl --install
   ```
   完了後、PCを再起動する
2. [Docker Desktop](https://www.docker.com/products/docker-desktop/) をインストール
   - インストール時に "Use WSL 2 instead of Hyper-V" にチェックが入っていることを確認
   - インストール後、Docker Desktopを起動し、初回のチュートリアル/サインイン画面を通過させる
3. 動作確認
   ```
   docker --version
   docker run hello-world
   ```
   `hello-world` のメッセージが出れば準備完了

### 最初に決めておくこと

- アプリ名とリポジトリ名
- 公開URLの形（例: `/u/[username]`）
- 習熟度の段階定義（後述の付録A）

## M0. 動くものを本番に出す

**目的**: デプロイの経路を先に作る。Supabaseはまだ触らない。
**目安**: 半日

### 手順

1. Next.js プロジェクトを作成する

   ```
   npx create-next-app@latest <プロジェクト名> \
     --typescript \
     --tailwind \
     --app \
     --eslint \
     --src-dir \
     --import-alias "@/*" \
     --use-npm
   ```

   | オプション | 内容 |
   |---|---|
   | `--typescript` | TypeScriptを有効化 |
   | `--tailwind` | Tailwind CSSを最初から組み込む |
   | `--app` | App Router（`src/app` 配下でルーティング）を使う |
   | `--eslint` | ESLint設定を追加 |
   | `--src-dir` | ソースを `src/` 配下にまとめる |
   | `--import-alias "@/*"` | `@/components/...` のような絶対パスimportを使えるようにする |
   | `--use-npm` | パッケージマネージャをnpmに固定する（無指定だと対話式で聞かれる） |

   フラグを付けずに `npx create-next-app@latest` だけ実行すると、これらを対話形式で一つずつ聞かれる。決め打ちしたい場合は上記のように渡す。

   > **注意**: プロジェクト名（≒ディレクトリ名）は npm の命名規則に従うため大文字を含められない。既存のディレクトリで直接作りたい場合は `<プロジェクト名>` に `.` を渡すが、ディレクトリ名に大文字が入っているとエラーになる（つまずきポイント参照）。

2. ローカルで起動し、トップページの文言を書き換える

   ```
   npm run dev
   ```

   `src/app/page.tsx` を編集して保存すると、ブラウザが自動でホットリロードされる
3. GitHubに新規リポジトリを作り、pushする
4. Vercel でそのリポジトリを import してデプロイする
5. 発行された `*.vercel.app` のURLを開く

### 完了条件

- [x] 公開URLで自分が書いた文言が表示される
- [x] GitHubにpushすると自動で再デプロイされる（Vercelのgithub連携により、以降のpushで自動反映される）

### つまずきポイント

- ビルドエラーはローカルで `next build` を通してから push すると早い
- 作業ディレクトリ名に大文字が含まれていると `create-next-app .` が npm 命名規則で失敗する。別名で作ってから中身を移動するか、`--use-npm` 実行前にディレクトリ名を小文字にしておく
- 新しい環境では git のグローバル `user.name` / `user.email` が未設定でコミットに失敗することがある。その場合はリポジトリ単位で設定すればよい

### 実施記録（2026-07-25）

- リポジトリ: [tech-stack-log](https://github.com/yotti773/tech-stack-log)（Public）
- 構成: Next.js 16 / React 19 / TypeScript / Tailwind CSS v4 / App Router / `src/` ディレクトリ
- Vercel import・公開URL確認まで完了: https://tech-stack-log.vercel.app/
- **M0完了（2026-07-25）**

## M1. ローカルDBとつなぐ

**目的**: Supabaseの「マイグレーション → 型生成」の流れを体に入れる。認証はまだやらない。
**目安**: 1週間

### 手順

1. Supabase CLI をインストールする
2. プロジェクト直下で初期化する
   ```
   supabase init
   supabase start
   ```
   Docker上にPostgresとAuthが立ち上がり、ローカルのURLとanon keyが表示される
3. 表示された値を `.env.local` に書く
   ```
   NEXT_PUBLIC_SUPABASE_URL=（ローカルのAPI URL）
   NEXT_PUBLIC_SUPABASE_ANON_KEY=（ローカルのanon key）
   ```
   `.env.local` が `.gitignore` に入っていることを確認する
4. マイグレーションを作る
   ```
   supabase migration new create_technologies
   ```
   生成されたSQLファイルに `technologies` テーブルを定義する（付録B参照）
5. 反映する
   ```
   supabase db reset
   ```
6. 型を生成する
   ```
   supabase gen types typescript --local > src/types/database.types.ts
   ```
7. Server Component から一覧を取得して表示する

### 完了条件

- [x] テーブルがマイグレーションファイルとして残っている
- [x] 生成した型を使ってデータを表示できている
- [x] `supabase db reset` でいつでも作り直せる

### つまずきポイント

- **管理画面のGUIから直接テーブルを作らないこと**。手元に定義が残らず、本番に反映できなくなる
- スキーマを変えたら毎回 `gen types` をやり直す。習慣にする
- **マイグレーションでテーブルを作っただけだと `anon` / `authenticated` ロールに権限がなく、`permission denied for table ...` になる**。RLSを有効にする前でも、Postgres標準の権限としてテーブルへの `grant` が必要。共有マスタのように誰でも読んでよいテーブルは、マイグレーション内で `grant select on table <テーブル名> to anon, authenticated;` を忘れずに書く
- `supabase gen types typescript --local > file` を実行すると、接続ログ（`Connecting to db 5432`）が生成ファイルの1行目に混入し、TypeScriptの構文エラーになることがある。生成後は必ずファイルの中身を確認する
- Windows環境でNext.jsの開発サーバーを重複起動すると、ポート3000を古いプロセスが掴んだままになることがある。`netstat -ano | findstr :3000` 等でPIDを特定して終了させる
- **本番のSupabaseプロジェクトを作るのはM6**。それまでVercel側には`NEXT_PUBLIC_SUPABASE_URL`等の環境変数が無いため、Server ComponentでSupabaseクライアントを無条件に作ると本番ビルドがクラッシュする。env変数の有無をチェックし、無い場合はデータ取得をスキップするようにガードしておく

### 実施記録（2026-07-25）

- Supabase CLIは `npm install -D supabase` でdevDependencyとして導入（グローバルインストールではなく `npx supabase` 経由で実行）
- `technologies` テーブルを作成し、動作確認用に `supabase/seed.sql` へ4件のシードデータ（Next.js, Supabase, TypeScript, Tailwind CSS）を投入
- トップページ（`src/app/page.tsx`）をServer Componentとして書き換え、`src/lib/supabase/server.ts` の簡易クライアント（`@supabase/supabase-js` の `createClient`、認証はまだ使わない）経由で一覧を取得・表示
- **M1完了（2026-07-25）**

## M2. ログインできるようにする

**目的**: Cookieベースのセッション管理を通す。ここが最初の関門。
**目安**: 1週間

### 手順

1. `@supabase/ssr` と `@supabase/supabase-js` を入れる
2. Supabaseクライアントを3つ作り分ける
   - **ブラウザ用** … Client Component から使う
   - **サーバー用** … Server Component / Server Actions から使う。Cookieを読む
   - **middleware用** … トークンを更新してCookieに書き戻す
3. `middleware.ts` を置き、全リクエストでセッションを更新する
4. ログイン画面を作る
   - 学習用途ならメールリンク（マジックリンク）が最も簡単
   - ローカルでは送信メールを Inbucket（`supabase start` が出すURL）で確認できる
5. ログイン後のページで、自分のメールアドレスを表示する

### 完了条件

- [x] ログインできる
- [x] **ページをリロードしてもログイン状態が保たれる**
- [x] ログアウトできる

### つまずきポイント

- 「リロードすると未ログインに戻る」はほぼ middleware 未設置か、Cookieの書き戻し漏れ
- Server Component ではCookieの書き込みができない。書き込みは middleware か Server Actions 側で行う
- `@supabase/ssr` は仕様変更が入りやすい。**必ず公式ドキュメントの最新サンプルを見ながら書く**
- **Next.js 16では`middleware.ts`が`proxy.ts`に名称変更されている**（機能は同じ）。関数名も`middleware`→`proxy`。AGENTS.mdの警告通り、`node_modules/next/dist/docs/`を見て初めて気づけた
- マジックリンクのメール本文はデフォルトだとGoTrue自身の検証エンドポイント（`/auth/v1/verify`）宛のリンクになる。SSR/PKCE構成で自前の`/auth/confirm`ルートに`verifyOtp`させたい場合は、`supabase/config.toml`の`[auth.email.template.magic_link]`でテンプレートを差し替える必要がある
- **`config.toml`の変更は`supabase start`実行中には反映されない**。`supabase stop` → `supabase start`で作り直すまで、Studioの表示もメールテンプレートも古いまま
- ローカルのメールテスト基盤は名前こそ`inbucket`コンテナだが、実体は **Mailpit** のAPI（`/api/v1/messages`, `/api/v1/message/{id}`）。過去の情報で見る`/api/v1/mailbox/{name}`は404になる
- 開発中は`localhost:3000`と`127.0.0.1:3000`でCookieが別ドメイン扱いになる。動作確認は`site_url`に合わせて`127.0.0.1`に統一する
- **実際にハマった不具合**: `/auth/confirm`でリダイレクト先を`new URL(request.url).origin`から組み立てていたところ、このNext.jsのバージョンでは`request.url`のホスト名が実際の接続先（例: `127.0.0.1:3000`）と一致せず、常に`http://localhost:3000`になってしまい、確認メールのリンク（`127.0.0.1`側）で確立したCookieと別オリジン扱いになって「ログイン中にならない」現象が起きた。`request.headers.get("host")`（や`x-forwarded-host`）は正しい値を持っていたので、`request.url`ではなくHostヘッダーからoriginを組み立てるように修正した

### 実施記録（2026-07-25）

- `@supabase/ssr` を導入し、Supabaseクライアントを3種類に分割
  - `src/lib/supabase/client.ts`（ブラウザ用、`createBrowserClient`）
  - `src/lib/supabase/server.ts`（Server Component/Server Actions用、`createServerClient` + `next/headers`の`cookies()`）
  - `src/lib/supabase/middleware.ts`（`updateSession`関数。`getClaims()`でトークンをリフレッシュしCookieに書き戻す）
- Next.js 16の名称変更に合わせ、`middleware.ts`ではなく`src/proxy.ts`を作成。本番でSupabase未設定（M6まで）でも素通りするようenv変数の有無をガード
- ログインはマジックリンク方式。`src/app/login/`にフォーム（`useActionState`）とServer Action（`signInWithOtp`）を実装
- マジックリンクのメールテンプレートを`supabase/templates/magic_link.html`でカスタマイズし、`/auth/confirm?token_hash=...&type=email`という自前のURLを踏ませる形に変更（`supabase/config.toml`の`[auth.email.template.magic_link]`で指定）
- `src/app/auth/confirm/route.ts`でトークンを`verifyOtp`し、成功したらトップページへリダイレクト
- ログアウトは`src/app/logout/actions.ts`の`signOut()` Server Action
- 動作確認は実際にブラウザを使わず、`curl`でOTP発行 → Mailpit APIでメール本文取得 → `/auth/confirm`のリンクを叩いてCookieを保存 → 同じCookieで`/`に再アクセスしログイン状態が保たれることを確認、という手順で一通り検証した
- **M2完了（2026-07-25）**

## M3. RLSを理解する ★最重要

**目的**: 行レベルセキュリティを、体感として理解する。
**目安**: 1週間

### 手順

1. `profiles` テーブルを作る（付録B参照）
   - `id` は `auth.users` の `id` を参照する
   - `username`、`display_name`、`bio`、`is_public` を持たせる
2. 新規登録時に `profiles` の行が自動で作られるようにする
   - トリガー（`auth.users` への insert をフックする）で作るのが定番
3. RLSを有効にする
   ```sql
   alter table profiles enable row level security;
   ```
4. ポリシーを2つ書く
   - SELECT: 全員が読める
   - UPDATE: `auth.uid() = id` のときだけ許可
5. **わざと壊して確認する**
   - 別ユーザーを作り、他人のプロフィールを更新してみる → 弾かれることを確認
   - ポリシーを一時的に外す → 更新できてしまうことを確認
   - 元に戻す

### 完了条件

- [x] 自分のプロフィールは編集できる
- [x] 他人のプロフィールは編集できない（実際に試して確認した）
- [x] RLSを外すとどうなるかを、自分の目で見た

### つまずきポイント

- **RLSを有効にしただけでポリシーを書かないと、全部拒否される**。「データが取れない」の大半はこれ
- `service_role` キーはRLSを完全に無視する。クライアント側には絶対に置かない
- ポリシーはテーブルごと・操作ごと（SELECT/INSERT/UPDATE/DELETE）に必要
- `service_role`キーであっても、テーブルへの`grant`が無ければ`permission denied`になる（M1の教訓の通り、RLSとGRANTは別レイヤー）
- **Supabase StudioのSQL Editorで`set role`や`set request.jwt.claims`を使って別ロールになりすます方法は信頼できない**。文ごとに接続が変わるらしく、セッション変数が次の文に引き継がれない。代わりにTable Editor右上の「View data as a role」→「Impersonate user」機能を使うと、実際のユーザーとしてRLSが適用された状態を確認できる
- UPDATEポリシーは`using`（どの行を更新対象にできるか）と`with check`（更新後の値がまだ条件を満たすか）の2つがある。`with check`を省略すると`using`と同じ条件が自動的に使われる
- ポリシー名は文字列（ダブルクォート）で書く。`update`のようなSQL予約語をそのまま名前にすると失敗する

### 実施記録（2026-07-25）

- `profiles`テーブルを作成し、`auth.users`への新規insertをフックするトリガー（`handle_new_user`）でサインアップ時に自動で行を作るようにした
- RLSを有効化し、SELECT（`using (true)`、誰でも読める）とUPDATE（`using (id = auth.uid())`、自分の行のみ）の2ポリシーを追加
- 「わざと壊して確認する」はユーザー自身がSupabase StudioのImpersonate機能で実施。自分の行は編集可・他人の行は編集不可を確認し、その後UPDATEポリシーを一時的に`using (true)`にして「誰でも編集できてしまう」無防備な状態も確認した上で、元のポリシーに戻した
- RLS・ポリシーはすべてマイグレーションファイル（`20260725061614_create_profiles.sql`）に反映済みで、`supabase db reset`で再現できることを確認
- **M3完了（2026-07-25）**

## M4. 書き込みと多対多

**目的**: Server Actions での書き込みと、中間テーブルの扱いを覚える。
**目安**: 2週間

### 手順

1. `user_technologies`（profile × technology）を作る（付録B参照）
   - 習熟度、経験年数、メモ、公開フラグを持たせる
   - `(profile_id, technology_id)` に一意制約をつける
2. RLSを設定する
   - SELECT: 公開フラグが立っているか、本人のもの
   - INSERT / UPDATE / DELETE: 本人のみ
3. Server Actions で登録・編集・削除を実装する
   - 保存後に `revalidatePath` で表示を更新する
4. 技術の追加UIを作る
   - `technologies` を検索して選ぶ
   - 無ければ新規追加できるようにする（同名チェックを入れる）
5. 一覧をカテゴリ別に表示する

### 完了条件

- [x] 技術を追加・編集・削除できる
- [x] 同じ技術を二重登録できない
- [x] カテゴリごとに整理されて表示される

### つまずきポイント

- 技術名は必ず共有マスタから選ばせる。自由入力にすると「React」「react」「React.js」が乱立し、フェーズ2の集計が成立しなくなる
- Server Actions は `"use server"` の付け忘れに注意
- SELECTポリシーは`is_public = true or profile_id = auth.uid()`のように**OR条件**にする（M3の単純な自分だけのケースと違う）。SQLの論理和は`or`であって、JS等の`||`ではない
- INSERTポリシーには`using`ではなく**`with check`のみ**を書く。まだ存在しない行なので「既存の行を対象にできるか」という`using`の概念がそもそも当てはまらない
- `technologies`（共有マスタ）はM1の時点でSELECTしか許可していなかったため、「無ければ新規追加」機能のために`grant insert on table technologies to authenticated;`を追加で必要とした
- RLSの`using`条件に合わない行へのUPDATE/DELETEは、エラーにはならず**静かに0件影響**で終わる（M1のGRANT拒否＝明示的エラー、とは対照的）

### 実施記録（2026-07-25）

- `user_technologies`テーブルを作成。習熟度は`smallint` + `check (level between 1 and 5)`で表現し、意味の定義（言葉）はアプリ側で持つ方針にした
- RLSポリシーはM3と同様、AIがヒントを出しながらユーザーが実際に書いた。「is_public = true or profile_id = auth.uid()」というOR条件のSELECTポリシー、`with check`のみのINSERTポリシーを実装
- 動作確認はSupabase Studioの2ユーザー分のテストデータを使い、INSERTで他人のprofile_idを詐称できないこと、他人の行のUPDATE/DELETEが（エラーではなく）0件影響で終わることを確認
- CRUD部分（Server Actions・`/mytech`ページ）はAIが実装。`curl`で実際にトークンを使い、新規技術追加・登録・二重登録の拒否・カテゴリ別表示・他人の行を更新できないことまで一通り検証した
- **M4完了（2026-07-25）**

### やったこと

## M5. 公開ページ

**目的**: 未認証ユーザー向けの読み取り経路を作る。
**目安**: 1週間

### 手順

1. `/u/[username]` のルートを作る
2. 未ログイン状態（anon）でデータを取得する
3. 公開フラグが立っているものだけが返ることを確認する
4. `revalidate` を設定してキャッシュを効かせる
5. OGP画像とメタタグを設定する

### 完了条件

- [x] ログアウト状態（またはシークレットウィンドウ）で自分のプロフィールが見える
- [x] 非公開にした技術が公開ページに出ていない

### 実施記録（2026-07-25）

- 着手前に`profiles`テーブルのRLSを見直した。SELECTポリシーが`using (true)`のままで、`is_public`に関わらず誰でも全ユーザーのプロフィール行を読める状態だったため（`user_technologies`はM4で正しく`is_public = true or profile_id = auth.uid()`というOR条件になっていたが、`profiles`側は追随していなかった）、同じ形のポリシーに修正するマイグレーションを追加した
- 加えて、ユーザーの希望でアプリ側のクエリでも`.eq("is_public", true)`を明示的に付ける「RLSとアプリ両方で守る」方針にした（RLSが唯一の防波堤にならないようにする多層防御）
- `/u/[username]`は未ログインの公開ページのため、Cookieを読まない専用クライアント（`src/lib/supabase/public.ts`、`@supabase/supabase-js`を直接使用）を新設した。既存の`server.ts`はCookie経由でセッションを扱うため、これを流用すると後述のキャッシュの問題が起きる
- 存在しない/非公開のusernameへのアクセスは`next/navigation`の`notFound()`で404にする方針にした（存在しないのか非公開なのかは区別せず伝えない）
- usernameは`/u/[username]`のURLに直接使われるため、`^[a-z0-9_-]{3,20}$`という簡易フォーマットチェックをプロフィール保存時に追加した（これまで未設定だった）
- OGP・メタタグは`generateMetadata`でtitle/description/openGraphのテキスト情報のみ設定した。動的なOGP画像生成は今回のスコープ外とした
- 習熟度の表示は、公開ページでは編集操作が不要なため、`.level-picker`とは別に非対話的な`.level-meter`（同じ見た目のブロック表示、ラジオボタン無し）を新設して使った

### つまずきポイント

- 「ログイン中は見えるのに、ログアウトすると見えない」はRLSのSELECTポリシーが本人限定になっているサイン
- キャッシュが効きすぎて更新が反映されない場合は、編集時に該当パスを `revalidatePath` する
- **`export const revalidate = 60` を付けても効かなかった**。原因は共通ヘッダー（`layout.tsx`）が毎リクエスト`cookies()`を読む設計になっており、これがアプリ全体（`/u/[username]`を含む）を動的レンダリングに強制しているため。`next build && next start` の後 `curl -i` で `Cache-Control` ヘッダーを見ると、`/technologies`のような既存ページも含めて全ページが `private, no-cache, no-store`（＝完全動的）になっていることを確認できた。ISR化するには共通ヘッダーを持たない専用layoutに分離する必要があるが、「常に同じヘッダーがある」という一貫性を優先し、今回は`revalidate`の指定を削除して「実質フル動的」で進めることにした

### 実施記録その4: SMTP制約により本番ログインを保留（2026-07-25）

手順6の途中で、**カスタムSMTPを設定しないかぎり本番のログインが成立しない**ことが判明した。3つの制約が噛み合っている。

1. **デフォルトSMTPはチームメンバー以外に送信しない**。公式ドキュメントに "Supabase Auth will refuse to deliver messages to addresses that are not part of the project's team" とある。送信数も1時間に2通。つまり自分以外は誰もログインできない
2. **このアプリの認証方式はテンプレート編集が必須**。`@supabase/ssr`はPKCEフローで、マジックリンクの公式ドキュメントに "If you're using PKCE flow, edit the Magic Link email template to send a token hash" と明記されている。デフォルトの`{{ .ConfirmationURL }}`はSupabase自身の検証エンドポイント向けなので、自前の`/auth/confirm`が成立しない
3. **そのテンプレート編集が、カスタムSMTPなしでは開放されない**。ダッシュボードに "Set up custom SMTP to edit templates" と表示される。SMTPのドキュメントページには「テンプレート編集にカスタムSMTPは不要」と書かれているが、ダッシュボードの実挙動が優先（ドキュメントが追いついていない）

そしてResendは送信にドメイン検証を要求する（"You must add and verify at least one domain to send and receive emails"）。**手順7で「任意」としていた独自ドメインが、実質的に必須に格上げされた**。

費用が絡む判断のためユーザーに確認し、**本番ログインはいったん保留**とした。認証不要の公開ページはすでに本番で動いているので、データはSQL Editorから直接投入して公開ページの確認まで進める。ログイン機能の開発はローカルで継続する。

### 実施記録その5: 認証方式をGitHub OAuth + パスワードに変更（2026-07-26）

SMTP制約への対処として、**メール送信を必要としない認証方式に切り替えた**。ユーザーの判断で両方式に対応。

- **メール + パスワード**: `enable_confirmations = false`（確認メールをオフ）なら、`signUp()`も`signInWithPassword()`もメールを1通も送らない。ローカルの`/auth/v1/settings`で`mailer_autoconfirm: true`を確認済み
- **GitHub OAuth**: `signInWithOAuth()`はサーバー側では遷移せず「飛ばすべきURL」を返すだけなので、こちらで`redirect(data.url)`する。戻り先の`/auth/callback`で`exchangeCodeForSession(code)`を呼ぶ
- **`/auth/confirm`と`/auth/callback`は別物**。前者はメールの`token_hash`を`verifyOtp()`で検証、後者はプロバイダから返る`code`を`exchangeCodeForSession()`で交換する。M2で混同した2つが、今回そろって実在することになったのでコメントで明示した
- `/auth/confirm`とマジックリンクのテンプレートは**残してある**。パスワード再設定（`type=recovery`）が同じ`token_hash`の仕組みを使うため、SMTPを設定したときにそのまま使える。マジックリンクのログインUIだけを外した（gitの履歴から復元可能）
- `next`パラメータは`startsWith("/")`で検証してからリダイレクトする（オープンリダイレクト防止）
- ログイン失敗時は「メールアドレスまたはパスワードが違います」とだけ返し、どちらが違うかは伝えない（アカウントの存在を推測させないため）

#### GitHub OAuth Appの登録（本番で必要）

GitHub → Settings → Developer settings → OAuth Apps → New OAuth App

- Homepage URL: `https://tech-stack-log.vercel.app`
- **Authorization callback URL: `https://gkyandnzavvoqhndtkje.supabase.co/auth/v1/callback`**

コールバック先は**アプリの`/auth/callback`ではなくSupabaseのURL**。GitHub → Supabase → アプリの順に戻ってくるため。

#### Supabaseダッシュボード側の設定場所（2026-07-26時点のUI）

Authentication のサイドバーは MANAGE / NOTIFICATIONS / CONFIGURATION に分かれている。必要なのは全部 CONFIGURATION 側。

| やること | 場所 |
|---|---|
| GitHubを有効化し Client ID / Secret を入れる | **Sign In / Providers** → GitHub |
| **Confirm email をオフ**（これを忘れるとサインアップで確認メールが飛ぶ） | **Sign In / Providers** → Email |
| Site URL / Redirect URLs | **URL Configuration** |

**MANAGE の「OAuth Apps」は別物**なので触らないこと。あれは Supabase 自身をOAuthサーバーとして外部アプリに認可を出す機能で、GitHubをログイン手段として使う設定ではない。

#### 検証結果（ローカル）

パスワードでの新規登録・ログアウト・再ログイン・保護ページへのアクセス・誤ったパスワードの拒否まで通し、コンソールエラーなし。GitHubログインは実際のOAuth App資格情報が要るため往復は未検証だが、`/auth/v1/authorize?provider=github&redirect_to=...&code_challenge=...`（PKCE）を経て`https://github.com/login/oauth/authorize`まで到達することを確認した。`/auth/callback`にcodeが無い場合はログイン画面へエラー付きで戻る。

### つまずきポイント

- **ログイン後に localhost に飛ばされる** → Auth の Site URL / Redirect URLs の設定漏れ
- **`has-text()`は部分一致**。自動テストで`button:has-text("ログイン")`と書くと「GitHub**でログイン**」にも当たる。厳密一致は`:text-is()`
- **メールのリンクを踏んでもログインできない** → Magic Link のメールテンプレートを本番に入れ忘れている（手順6-2）。`db push`はDBしか運ばない
- 本番と開発でSupabaseプロジェクトを分ける。無料枠は2プロジェクトまでなので、ちょうど収まる
- 無料プランは7日間アクセスがないと自動停止する。再開は管理画面から手動で行う
- 無料プランの組み込みSMTPは送信数が厳しく絞られている（検証で何度もログインし直すとすぐ頭打ちになる）。継続的に使うなら Resend 等のカスタムSMTPを設定する
- **`127.0.0.1:3000`でアクセスするとフォームが動かない**。Next.jsのdevサーバーは`localhost:3000`で待ち受けているため、`127.0.0.1`は別オリジン扱いになりdevリソース（HMR等）がブロックされ、ハイドレーションが完走しない。ハイドレーションしないと`useActionState`のフォームはJSなしの経路（ネイティブPOST）にフォールバックし、送信してもメッセージが出ないまま303でトップに飛ぶ。`supabase/config.toml`の`site_url`が`http://127.0.0.1:3000`なのでマジックリンクは127.0.0.1側に着地する点に注意（ローカル確認時は`localhost`に開き直すか、`site_url`を`localhost:3000`に揃える）
- 自動テストでフォームを操作するときは、**ヘッダーのログアウトボタンもDOM順で先に来る`button[type="submit"]`である**ことに注意。セレクタをラベルで絞らないとログアウトを押してしまい、「セッションが切れる → トップに飛ぶ」という上記と同じ症状に見える
