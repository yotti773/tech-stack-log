# 技術スタック整理アプリ 構築手順書（フェーズ1）

Next.js + Supabase で、自分の略歴と技術習熟度を登録・公開できるアプリを作る。
学習目的のため、**1マイルストーンにつき新しい概念は1つだけ**という方針で並べている。

- 想定稼働: 週10時間
- 想定期間: 約8週間（M0〜M6）
- ゴール: 公開URLで自分のスタックと略歴が見える状態

---

## 0. 前提と準備

### 用意するもの

| もの | 用途 | 費用 |
|---|---|---|
| Node.js（LTS版） | Next.js の実行 | 無料 |
| Docker Desktop | ローカルSupabaseの起動 | 無料 |
| GitHubアカウント | ソース管理・デプロイ連携 | 無料 |
| Vercelアカウント | ホスティング | 無料（Hobby） |
| Supabaseアカウント | DB・認証 | 無料 |

> **注意**: Vercel Hobby は非商用・個人利用に限定されている。
> リポジトリは「個人アカウント所有」にすること。Git組織所有のリポジトリは Hobby では接続できない。

### 最初に決めておくこと

- アプリ名とリポジトリ名
- 公開URLの形（例: `/u/[username]`）
- 習熟度の段階定義（後述の付録A）

## M0. 動くものを本番に出す

**目的**: デプロイの経路を先に作る。Supabaseはまだ触らない。
**目安**: 半日

### 手順

1. Next.js プロジェクトを作成する
   - App Router を選ぶ
   - TypeScript を有効にする
   - Tailwind CSS は入れておくと後がラク
2. ローカルで起動し、トップページの文言を書き換える
3. GitHubに新規リポジトリを作り、pushする
4. Vercel でそのリポジトリを import してデプロイする
5. 発行された `*.vercel.app` のURLを開く

### 完了条件

- [x] 公開URLで自分が書いた文言が表示される
- [x] GitHubにpushすると自動で再デプロイされる（Vercelのgithub連携により、以降のpushで自動反映される）

### つまずきポイント

- ビルドエラーはローカルで `next build` を通してから push すると早い
- 作業ディレクトリ名に大文字が含まれていると `create-next-app .` が npm 命名規則で失敗する。別名で作ってから中身を移動するか、`--use-npm` 実行前にディレクトリ名を小文字にしておく
- 新しい環境では git のグローバル `user.name` / `user.email` が未設定でコミットに失敗することがある。その場合はリポジトリ単位で設定すればよい

## M1. ローカルDBとつなぐ

**目的**: Supabaseの「マイグレーション → 型生成」の流れを体に入れる。認証はまだやらない。
**目安**: 1週間

### 手順

1. Supabase CLI をインストールする
2. プロジェクト直下で初期化する
   ```
   supabase init
   supabase start
   ```
   Docker上にPostgresとAuthが立ち上がり、ローカルのURLとanon keyが表示される
3. 表示された値を `.env.local` に書く
   ```
   NEXT_PUBLIC_SUPABASE_URL=（ローカルのAPI URL）
   NEXT_PUBLIC_SUPABASE_ANON_KEY=（ローカルのanon key）
   ```
   `.env.local` が `.gitignore` に入っていることを確認する
4. マイグレーションを作る
   ```
   supabase migration new create_technologies
   ```
   生成されたSQLファイルに `technologies` テーブルを定義する（付録B参照）
5. 反映する
   ```
   supabase db reset
   ```
6. 型を生成する
   ```
   supabase gen types typescript --local > src/types/database.types.ts
   ```
7. Server Component から一覧を取得して表示する

### 完了条件

- [ ] テーブルがマイグレーションファイルとして残っている
- [ ] 生成した型を使ってデータを表示できている
- [ ] `supabase db reset` でいつでも作り直せる

### つまずきポイント

- **管理画面のGUIから直接テーブルを作らないこと**。手元に定義が残らず、本番に反映できなくなる
- スキーマを変えたら毎回 `gen types` をやり直す。習慣にする

## M2. ログインできるようにする

**目的**: Cookieベースのセッション管理を通す。ここが最初の関門。
**目安**: 1週間

### 手順

1. `@supabase/ssr` と `@supabase/supabase-js` を入れる
2. Supabaseクライアントを3つ作り分ける
   - **ブラウザ用** … Client Component から使う
   - **サーバー用** … Server Component / Server Actions から使う。Cookieを読む
   - **middleware用** … トークンを更新してCookieに書き戻す
3. `middleware.ts` を置き、全リクエストでセッションを更新する
4. ログイン画面を作る
   - 学習用途ならメールリンク（マジックリンク）が最も簡単
   - ローカルでは送信メールを Inbucket（`supabase start` が出すURL）で確認できる
5. ログイン後のページで、自分のメールアドレスを表示する

### 完了条件

- [ ] ログインできる
- [ ] **ページをリロードしてもログイン状態が保たれる**
- [ ] ログアウトできる

### つまずきポイント

- 「リロードすると未ログインに戻る」はほぼ middleware 未設置か、Cookieの書き戻し漏れ
- Server Component ではCookieの書き込みができない。書き込みは middleware か Server Actions 側で行う
- `@supabase/ssr` は仕様変更が入りやすい。**必ず公式ドキュメントの最新サンプルを見ながら書く**

## M3. RLSを理解する ★最重要

**目的**: 行レベルセキュリティを、体感として理解する。
**目安**: 1週間

### 手順

1. `profiles` テーブルを作る（付録B参照）
   - `id` は `auth.users` の `id` を参照する
   - `username`、`display_name`、`bio`、`is_public` を持たせる
2. 新規登録時に `profiles` の行が自動で作られるようにする
   - トリガー（`auth.users` への insert をフックする）で作るのが定番
3. RLSを有効にする
   ```sql
   alter table profiles enable row level security;
   ```
4. ポリシーを2つ書く
   - SELECT: 全員が読める
   - UPDATE: `auth.uid() = id` のときだけ許可
5. **わざと壊して確認する**
   - 別ユーザーを作り、他人のプロフィールを更新してみる → 弾かれることを確認
   - ポリシーを一時的に外す → 更新できてしまうことを確認
   - 元に戻す

### 完了条件

- [ ] 自分のプロフィールは編集できる
- [ ] 他人のプロフィールは編集できない（実際に試して確認した）
- [ ] RLSを外すとどうなるかを、自分の目で見た

### つまずきポイント

- **RLSを有効にしただけでポリシーを書かないと、全部拒否される**。「データが取れない」の大半はこれ
- `service_role` キーはRLSを完全に無視する。クライアント側には絶対に置かない
- ポリシーはテーブルごと・操作ごと（SELECT/INSERT/UPDATE/DELETE）に必要

## M4. 書き込みと多対多

**目的**: Server Actions での書き込みと、中間テーブルの扱いを覚える。
**目安**: 2週間

### 手順

1. `user_technologies`（profile × technology）を作る（付録B参照）
   - 習熟度、経験年数、メモ、公開フラグを持たせる
   - `(profile_id, technology_id)` に一意制約をつける
2. RLSを設定する
   - SELECT: 公開フラグが立っているか、本人のもの
   - INSERT / UPDATE / DELETE: 本人のみ
3. Server Actions で登録・編集・削除を実装する
   - 保存後に `revalidatePath` で表示を更新する
4. 技術の追加UIを作る
   - `technologies` を検索して選ぶ
   - 無ければ新規追加できるようにする（同名チェックを入れる）
5. 一覧をカテゴリ別に表示する

### 完了条件

- [ ] 技術を追加・編集・削除できる
- [ ] 同じ技術を二重登録できない
- [ ] カテゴリごとに整理されて表示される

### つまずきポイント

- 技術名は必ず共有マスタから選ばせる。自由入力にすると「React」「react」「React.js」が乱立し、フェーズ2の集計が成立しなくなる
- Server Actions は `"use server"` の付け忘れに注意

## M5. 公開ページ

**目的**: 未認証ユーザー向けの読み取り経路を作る。
**目安**: 1週間

### 手順

1. `/u/[username]` のルートを作る
2. 未ログイン状態（anon）でデータを取得する
3. 公開フラグが立っているものだけが返ることを確認する
4. `revalidate` を設定してキャッシュを効かせる
5. OGP画像とメタタグを設定する

### 完了条件

- [ ] ログアウト状態（またはシークレットウィンドウ）で自分のプロフィールが見える
- [ ] 非公開にした技術が公開ページに出ていない

### つまずきポイント

- 「ログイン中は見えるのに、ログアウトすると見えない」はRLSのSELECTポリシーが本人限定になっているサイン
- キャッシュが効きすぎて更新が反映されない場合は、編集時に該当パスを `revalidatePath` する

## M6. 略歴と本番公開

**目的**: 残りの機能を足し、本番環境に載せる。
**目安**: 2週間

### 手順

1. `careers`（略歴）と `career_technologies` を作る
2. 略歴の登録・編集を実装する（M4と同じ流れ）
3. Supabase のクラウドプロジェクトを作る
4. ローカルのマイグレーションを本番に適用する
   ```
   supabase link --project-ref （プロジェクトID）
   supabase db push
   ```
5. Vercel の環境変数に本番のURLとanon keyを設定する
6. Supabase の Auth 設定で、本番URLをリダイレクト許可リストに追加する
7. 独自ドメインを設定する（任意）

### 完了条件

- [ ] 本番URLでログインして、自分のデータを登録できる
- [ ] 公開ページが第三者から見える

### つまずきポイント

- **ログイン後に localhost に飛ばされる** → Auth の Site URL / Redirect URLs の設定漏れ
- 本番と開発でSupabaseプロジェクトを分ける。無料枠は2プロジェクトまでなので、ちょうど収まる
- 無料プランは7日間アクセスがないと自動停止する。再開は管理画面から手動で行う

## 付録A. 習熟度の定義（案）

フェーズ2で分布を集計したときに意味のある数字にするため、言葉で基準を決めておく。

| レベル | 定義 |
|---|---|
| 1 | 触ったことがある |
| 2 | チュートリアル程度なら書ける |
| 3 | 業務で使ったことがある |
| 4 | 一人で設計・判断できる |
| 5 | 人に教えられる |

## 付録B. テーブル構成（フェーズ1）

```
profiles              … auth.users と1対1
  id, username, display_name, bio, is_public

technologies          … 共有マスタ
  id, name, category, official_url

user_technologies     … profiles × technologies
  id, profile_id, technology_id, level, years, note, is_public
  unique(profile_id, technology_id)

careers               … 略歴
  id, profile_id, company, role, started_on, ended_on, summary, is_public

career_technologies   … careers × technologies
  career_id, technology_id
```

**設計上の固定事項**

- `technologies` は共有マスタにする（フェーズ2の集計の前提）
- 公開フラグは行ごとに持たせる（RLSで使う）

## 付録D. 進め方のコツ

- **M3で必ず立ち止まる**。RLSが腹落ちしないまま先に進むと、後で全部作り直しになる
- 機能を足したくなったら、まずメモに書いて次のフェーズに送る
- 詰まったら「どのレイヤーの問題か」を切り分ける
  1. SQLエディタで直接クエリを叩く → DBの問題か？
  2. RLSを一時的に外す → ポリシーの問題か？
  3. サーバーログを見る → Next.js側の問題か？
- `@supabase/ssr` と Next.js App Router は変化が速い。手順書の記述と公式ドキュメントが食い違ったら、**公式を優先する**
