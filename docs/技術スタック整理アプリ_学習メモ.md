## M1: Supabaseマイグレーションの仕組み

### マイグレーションはどう管理されているか

`supabase/migrations/` の中のファイル名（例: `20260725043455_create_technologies.sql`）
の先頭はタイムスタンプで、これが適用順を決める。

DB内部には `supabase_migrations.schema_migrations` という管理用テーブルがあり、
「どのバージョンまで適用済みか」を記録している。

- `supabase db reset`（ローカル）: DBを空にして、`migrations/` を最初から全部再生する
- `supabase db push`（本番向け、M6で使う）: 本番の管理テーブルを見て、**まだ適用されていないファイルだけ**を順に適用する

マイグレーションファイルは「スキーマを組み立てる、順序付きのレシピ集」。

### バージョン管理すべきか

すべき。理由は3つ。

1. 本番に何が入っているか、ファイルを見れば分かる（GUIでテーブルを作ると失われる）
2. `db push` は「まだ当てていない分」を機械的に判定するので、gitで管理されていないと本番の適用状況を誰も追えなくなる
3. 一度チームや本番に適用したファイルは後から書き換えない。変更したくなったら新しいファイルを追加する（gitのコミットを書き換えないのと同じ発想）。ただしまだ誰にも適用していない段階なら、直接直しても実害はない

### `migrations/` と `seed.sql` の違い

`supabase/config.toml` の `[db.seed]` セクションがこの違いの実体。

```toml
[db.seed]
enabled = true
sql_paths = ["./seed.sql"]
```

| | migrations/ | seed.sql |
|---|---|---|
| 中身 | DDL（`create table` 等＝スキーマの定義） | DML（`insert` 等＝実際のデータ） |
| 役割 | 「箱」の形。環境間で同一であるべき | 「箱」の中身。ローカル動作確認用のサンプルデータ |
| `db push`（本番反映）で実行される？ | される | **されない** |
| `db reset`（ローカル）で実行される？ | される | される（migrationsの後） |

seed.sqlは意図的に「本番には絶対届かない場所」に置かれている。migrationsフォルダの中に
insert文を混ぜると、本番pushの対象になり、ダミーデータが本物のDBに入ってしまう。
さらに `unique` 制約などがあると、2回目以降のpushで一意制約違反になり得る。

### seed.sqlはなぜ1ファイルのまま育てるのか

migrationsとseedでは「時間」の扱いが違う。

- migrations: 過去の変更の**積み重ね**。ファイルを追加していく
- seed.sql: 今ほしいサンプルデータの**完成形**。`db reset` のたびに全部を1から流し込む。積み重ねという概念がそもそも無い

なので、seedは基本的に中身を直接書き換えていくもの。ただし整理整頓のために分割はできる。
`config.toml` の `sql_paths` はglobパターンにも対応しているので、テーブルが増えて
1ファイルが読みにくくなったら `sql_paths = ["./seeds/*.sql"]` に変えて
`supabase/seeds/technologies.sql` のようにテーブルごとへ分割できる（バージョンの積み重ねではなく、ファイル整理の目的）。

`seed.sql` が `migrations/` フォルダに入っていないのも同じ理由。migrationsの一種に
見えてしまうと「本番にpushされる」誤解を招くため、あえて `supabase/` 直下に置いて
別物だと視覚的にも分かるようにしてある。

### テストデータが増えて複雑になったら

複雑さの主因はファイル数ではなく、**テーブルが増えて外部キーで依存し合うこと**
（M3の`profiles`、M4の`user_technologies`など）。対処の方向性:

- ファイルを分けたいだけなら `seeds/*.sql` で十分
- IDを跨ぐ関連が増えて辛くなったら、ハードコードしたUUIDではなく
  `insert ... select id from technologies where name = 'Next.js'` のように
  **名前で引く**形にしておくと依存関係が壊れにくい
- 生SQLのseedは「読めば全部わかる」単純さが利点だが、大量データや複雑な関連には向かない。
  その域に達したらsupabase-js経由のTypeScriptスクリプトへの切り替えも選択肢だが、
  それはSQLだけで完結する単純さを手放すことになるトレードオフがある

## M2: ローカル環境だとメールはどこに行くのか

### ローカルではメールは実際に届かない

`signInWithOtp`（マジックリンクログイン）を呼ぶと、Supabase Authはメールを送ろうとする。
ただしローカル環境では、本物のメールボックスには一切届かない。これは意図的な仕様。

`supabase/config.toml` の `[local_smtp]` セクション（`enabled = true`, `port = 54324`）が
「メールは外部に送らず、テスト用の受信箱に溜めておく」よう指示している。実体は
**Mailpit** というメールキャッチャーで、GoTrueは本物のSMTPサーバーの代わりにこの
Mailpitへメールを渡す。

なお、このコンテナはCLI上では歴史的経緯で `inbucket` という名前のままだが（`docker ps`で
`supabase_inbucket_...` と表示される）、中身は現在Mailpitに置き換わっている。API仕様も
Mailpitのもの（`/api/v1/messages`, `/api/v1/message/{id}`）で、古い情報にある
`/api/v1/mailbox/{name}` のようなInbucket形式のエンドポイントは404になる。

### 確認方法

- ブラウザで http://127.0.0.1:54324 を開くとWeb UIがあり、届いたメールを一覧・閲覧できる
- API越しに直接取得することも可能（`curl`でM2の動作確認をした際はこちらを使った）

### 実際に自分宛にメールを受け取りたい場合

`config.toml`の`[auth.email.smtp]`セクション（デフォルトはコメントアウト）に本物の
SMTP認証情報（SendGrid等）を設定すれば、ローカルでも実際のメールが送られるようになる。

### 本番（M6）ではどうなるか

Vercel + 本番Supabaseの構成になった時点で、この`local_smtp`の仕組みは使われなくなる。
本番では別途SMTPプロバイダを設定するか、Supabase純正のメール送信（無料枠はあるが
レート制限が厳しい）を使うことになる。これはM6のタスク。

## M2: マジックリンクから戻ってもログイン中にならなかった話

### 症状

メール内のリンク（`/auth/confirm?token_hash=...`）を踏んでトップページにリダイレクトされても、
ログイン状態が反映されない。エラーも出ない。

### 原因

`/auth/confirm`のルートハンドラで、リダイレクト先を次のように組み立てていた。

```ts
const { searchParams, origin } = new URL(request.url);
// ...
return NextResponse.redirect(`${origin}${next}`);
```

`request.url`は「今どのURLにリクエストが来たか」を表すはずのプロパティだが、
今回使っているNext.jsのバージョンでは、ローカル開発時に**実際の接続先ホスト名を反映せず、
常に`http://localhost:3000`になる**という挙動が確認できた（`curl`で`127.0.0.1:3000`に
アクセスしても、サーバー側で`request.url`をログ出力すると`localhost:3000`になっていた）。

一方、Supabaseのセッションを保持するCookieは、確認リンクを実際に踏んだホスト
（メールテンプレートの`{{ .SiteURL }}`＝`config.toml`の`site_url` = `127.0.0.1:3000`）
に対して発行される。

つまり:

1. `127.0.0.1:3000/auth/confirm` にアクセス → Cookieは`127.0.0.1`に対して発行される
2. リダイレクト先は`request.url`由来の`localhost:3000` → **別オリジン**
3. ブラウザは`localhost:3000`に飛ばされるが、そこには`127.0.0.1`用のCookieは送られない
4. 結果、ログイン状態が見えない

### 気づき方

`request.headers.get("host")`を別途ログ出力すると、こちらは`127.0.0.1:3000`と正しい値を
返していた。`request.url`だけがずれていることから、Next.js側の実装依存の挙動だと判断できた。

### 対処

`request.url`ではなく、実際に届いた`Host`ヘッダー（`x-forwarded-host`があればそちら優先、
本番でリバースプロキシを経由する場合を想定）からoriginを組み立てるようにした。

```ts
const host =
  request.headers.get("x-forwarded-host") ?? request.headers.get("host");
const protocol = request.headers.get("x-forwarded-proto") ?? "http";
const origin = `${protocol}://${host}`;
```

Hostヘッダーはリバースプロキシ（Vercelなど）を挟んでも`x-forwarded-host`に引き継がれるため、
本番でも同じロジックで動く。「`request.url`のoriginが信用できないことがある」という点は
一般的な注意点でもあり、Route Handlerでリダイレクト先を組み立てるときは、まずHostヘッダーを
使う方が安全だと分かった。
