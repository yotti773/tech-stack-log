## M1: Supabaseマイグレーションの仕組み

### マイグレーションはどう管理されているか

`supabase/migrations/` の中のファイル名（例: `20260725043455_create_technologies.sql`）
の先頭はタイムスタンプで、これが適用順を決める。

DB内部には `supabase_migrations.schema_migrations` という管理用テーブルがあり、
「どのバージョンまで適用済みか」を記録している。

- `supabase db reset`（ローカル）: DBを空にして、`migrations/` を最初から全部再生する
- `supabase db push`（本番向け、M6で使う）: 本番の管理テーブルを見て、**まだ適用されていないファイルだけ**を順に適用する

マイグレーションファイルは「スキーマを組み立てる、順序付きのレシピ集」。

### バージョン管理すべきか

すべき。理由は3つ。

1. 本番に何が入っているか、ファイルを見れば分かる（GUIでテーブルを作ると失われる）
2. `db push` は「まだ当てていない分」を機械的に判定するので、gitで管理されていないと本番の適用状況を誰も追えなくなる
3. 一度チームや本番に適用したファイルは後から書き換えない。変更したくなったら新しいファイルを追加する（gitのコミットを書き換えないのと同じ発想）。ただしまだ誰にも適用していない段階なら、直接直しても実害はない

### `migrations/` と `seed.sql` の違い

`supabase/config.toml` の `[db.seed]` セクションがこの違いの実体。

```toml
[db.seed]
enabled = true
sql_paths = ["./seed.sql"]
```

| | migrations/ | seed.sql |
|---|---|---|
| 中身 | DDL（`create table` 等＝スキーマの定義） | DML（`insert` 等＝実際のデータ） |
| 役割 | 「箱」の形。環境間で同一であるべき | 「箱」の中身。ローカル動作確認用のサンプルデータ |
| `db push`（本番反映）で実行される？ | される | **されない** |
| `db reset`（ローカル）で実行される？ | される | される（migrationsの後） |

seed.sqlは意図的に「本番には絶対届かない場所」に置かれている。migrationsフォルダの中に
insert文を混ぜると、本番pushの対象になり、ダミーデータが本物のDBに入ってしまう。
さらに `unique` 制約などがあると、2回目以降のpushで一意制約違反になり得る。

### seed.sqlはなぜ1ファイルのまま育てるのか

migrationsとseedでは「時間」の扱いが違う。

- migrations: 過去の変更の**積み重ね**。ファイルを追加していく
- seed.sql: 今ほしいサンプルデータの**完成形**。`db reset` のたびに全部を1から流し込む。積み重ねという概念がそもそも無い

なので、seedは基本的に中身を直接書き換えていくもの。ただし整理整頓のために分割はできる。
`config.toml` の `sql_paths` はglobパターンにも対応しているので、テーブルが増えて
1ファイルが読みにくくなったら `sql_paths = ["./seeds/*.sql"]` に変えて
`supabase/seeds/technologies.sql` のようにテーブルごとへ分割できる（バージョンの積み重ねではなく、ファイル整理の目的）。

`seed.sql` が `migrations/` フォルダに入っていないのも同じ理由。migrationsの一種に
見えてしまうと「本番にpushされる」誤解を招くため、あえて `supabase/` 直下に置いて
別物だと視覚的にも分かるようにしてある。

### テストデータが増えて複雑になったら

複雑さの主因はファイル数ではなく、**テーブルが増えて外部キーで依存し合うこと**
（M3の`profiles`、M4の`user_technologies`など）。対処の方向性:

- ファイルを分けたいだけなら `seeds/*.sql` で十分
- IDを跨ぐ関連が増えて辛くなったら、ハードコードしたUUIDではなく
  `insert ... select id from technologies where name = 'Next.js'` のように
  **名前で引く**形にしておくと依存関係が壊れにくい
- 生SQLのseedは「読めば全部わかる」単純さが利点だが、大量データや複雑な関連には向かない。
  その域に達したらsupabase-js経由のTypeScriptスクリプトへの切り替えも選択肢だが、
  それはSQLだけで完結する単純さを手放すことになるトレードオフがある

## M2: ローカル環境だとメールはどこに行くのか

### ローカルではメールは実際に届かない

`signInWithOtp`（マジックリンクログイン）を呼ぶと、Supabase Authはメールを送ろうとする。
ただしローカル環境では、本物のメールボックスには一切届かない。これは意図的な仕様。

`supabase/config.toml` の `[local_smtp]` セクション（`enabled = true`, `port = 54324`）が
「メールは外部に送らず、テスト用の受信箱に溜めておく」よう指示している。実体は
**Mailpit** というメールキャッチャーで、GoTrueは本物のSMTPサーバーの代わりにこの
Mailpitへメールを渡す。

なお、このコンテナはCLI上では歴史的経緯で `inbucket` という名前のままだが（`docker ps`で
`supabase_inbucket_...` と表示される）、中身は現在Mailpitに置き換わっている。API仕様も
Mailpitのもの（`/api/v1/messages`, `/api/v1/message/{id}`）で、古い情報にある
`/api/v1/mailbox/{name}` のようなInbucket形式のエンドポイントは404になる。

### 確認方法

- ブラウザで http://127.0.0.1:54324 を開くとWeb UIがあり、届いたメールを一覧・閲覧できる
- API越しに直接取得することも可能（`curl`でM2の動作確認をした際はこちらを使った）

### 実際に自分宛にメールを受け取りたい場合

`config.toml`の`[auth.email.smtp]`セクション（デフォルトはコメントアウト）に本物の
SMTP認証情報（SendGrid等）を設定すれば、ローカルでも実際のメールが送られるようになる。

### 本番（M6）ではどうなるか

Vercel + 本番Supabaseの構成になった時点で、この`local_smtp`の仕組みは使われなくなる。
本番では別途SMTPプロバイダを設定するか、Supabase純正のメール送信（無料枠はあるが
レート制限が厳しい）を使うことになる。これはM6のタスク。

## M2: マジックリンクから戻ってもログイン中にならなかった話

### 症状

メール内のリンク（`/auth/confirm?token_hash=...`）を踏んでトップページにリダイレクトされても、
ログイン状態が反映されない。エラーも出ない。

### 原因

`/auth/confirm`のルートハンドラで、リダイレクト先を次のように組み立てていた。

```ts
const { searchParams, origin } = new URL(request.url);
// ...
return NextResponse.redirect(`${origin}${next}`);
```

`request.url`は「今どのURLにリクエストが来たか」を表すはずのプロパティだが、
今回使っているNext.jsのバージョンでは、ローカル開発時に**実際の接続先ホスト名を反映せず、
常に`http://localhost:3000`になる**という挙動が確認できた（`curl`で`127.0.0.1:3000`に
アクセスしても、サーバー側で`request.url`をログ出力すると`localhost:3000`になっていた）。

一方、Supabaseのセッションを保持するCookieは、確認リンクを実際に踏んだホスト
（メールテンプレートの`{{ .SiteURL }}`＝`config.toml`の`site_url` = `127.0.0.1:3000`）
に対して発行される。

つまり:

1. `127.0.0.1:3000/auth/confirm` にアクセス → Cookieは`127.0.0.1`に対して発行される
2. リダイレクト先は`request.url`由来の`localhost:3000` → **別オリジン**
3. ブラウザは`localhost:3000`に飛ばされるが、そこには`127.0.0.1`用のCookieは送られない
4. 結果、ログイン状態が見えない

### 気づき方

`request.headers.get("host")`を別途ログ出力すると、こちらは`127.0.0.1:3000`と正しい値を
返していた。`request.url`だけがずれていることから、Next.js側の実装依存の挙動だと判断できた。

### 対処

`request.url`ではなく、実際に届いた`Host`ヘッダー（`x-forwarded-host`があればそちら優先、
本番でリバースプロキシを経由する場合を想定）からoriginを組み立てるようにした。

```ts
const host =
  request.headers.get("x-forwarded-host") ?? request.headers.get("host");
const protocol = request.headers.get("x-forwarded-proto") ?? "http";
const origin = `${protocol}://${host}`;
```

Hostヘッダーはリバースプロキシ（Vercelなど）を挟んでも`x-forwarded-host`に引き継がれるため、
本番でも同じロジックで動く。「`request.url`のoriginが信用できないことがある」という点は
一般的な注意点でもあり、Route Handlerでリダイレクト先を組み立てるときは、まずHostヘッダーを
使う方が安全だと分かった。

### そもそもなぜ公式の書き方と違っていたのか

振り返ると、実装時にSupabase公式チュートリアルの**別のユースケース向けサンプル**と
混同していたことが根本原因だった。

- **マジックリンク確認用の`/auth/confirm`（今回の用途）**: 本来は`next/navigation`の
  `redirect(next)`という相対パスのリダイレクトで十分で、originを自分で組み立てる必要がない
- **OAuthコールバック用の`/auth/callback`（別の用途）**: OAuthプロバイダから絶対URLで
  コールバックされる都合上、`NextResponse.redirect`で絶対URLを組み立てる必要があり、
  その中で`x-forwarded-host`を見るという、もう少し複雑なパターンになっている

今回は前者で十分だったのに、後者寄りの「originを手で組み立てて`NextResponse.redirect`する」
書き方を採用してしまい、不要に複雑にした結果そのorigin計算自体にバグを持ち込んだ。

加えて、実装時にWebFetchで公式ドキュメントの当該ページを取得しようとしたが、フレームワーク別の
タブ切り替えで表示されるコードサンプルがうまく取得できず、記憶にあるパターンで書いてしまった、
という経緯もある。Supabaseクライアントの生成部分（`createServerClient`など）は
`node_modules/@supabase/ssr/src`のソースを直接読んで確実に検証したが、ルートハンドラの
「書き方の方針」はパッケージのソースには含まれないため、同じやり方では検証できなかった。

**教訓**: `node_modules`にソースがない「実装方針・パターン」は型定義を読むだけでは検証できない。
似て非なる公式サンプル（今回のOAuth用/マジックリンク用のように）を混同しないよう、
どのユースケース向けの説明かを確認してから実装し、書いた後は実際にエンドツーエンドで
動かして確認する。この方針は`CLAUDE.md`にも開発ルールとして追記した（2026-07-25）。

## M3: RLSを体感する

### `enable row level security`した直後、ポリシーが0件だとどうなるか

直感的には「ルールを何も決めていないから、今までと変わらない」と思ってしまいがちだが、
実際は逆で **ポリシー0件はデフォルトで全拒否** になる。

- RLSを有効にする前: アクセス可否は`grant`（テーブル単位の粗い許可）だけで決まる
- RLSを有効にした瞬間: `grant`に加えて「行ごとに、ポリシーが許可しているか」も毎回チェックされる
- ポリシーが1つも無ければ、その判定は常に`false`。`grant`で許可されていたはずのSELECT/UPDATEも、
  自分の行も含めて全部弾かれる（`service_role`キーだけはRLSごと無視できる例外）

これはPostgreSQLの「fail-closed（安全側に倒す）」という設計思想で、`set role anon;`のあと
`select * from profiles;`を実行すると`No rows returned`になることで実際に確認できた。

### UPDATEポリシーの`using`と`with check`

UPDATE用のポリシーには2つの判定軸がある。

- `using`: どの**既存の行**を更新対象にできるか
- `with check`: 更新した**後の新しい値**が、まだ条件を満たしているか

`with check`を省略すると`using`と同じ条件が自動的に使われる。今回の`profiles`のように
「自分の行だけ更新できればいい」という単純なケースでは意識しなくても動くが、M4で
「他人のprofile_idを持つ行をINSERTさせない」のような場面では、この2つを意識して
書き分ける必要が出てくる。

### Supabase StudioのSQL Editorで別ユーザーになりすます方法は信頼できない

RLSをテストするために、SQL Editorで次のようなことを試した。

```sql
set role authenticated;
set request.jwt.claims to '{"sub": "<uuid>", "role": "authenticated"}';
update profiles set bio = 'x' where id = '<他人のuuid>';
reset role;
```

一見動きそうに見えるが、実際には`set role`後に`select current_user;`しても`postgres`のまま、
`auth.uid()`も`null`のままだった。StudioのSQL Editorは複数文をまとめて実行しても、内部的には
文ごとに別の接続を使っているらしく、`set`で変更したセッション変数が次の文に引き継がれない。

代わりに、StudioのTable Editor右上にある **「View data as a role」→「Impersonate user」** 機能を
使うと、実際に存在するユーザーとしてRLSが適用された状態でTable Editorが見える。こちらは
Studio自身が正しくその人になりすましたリクエストを組み立てているため信頼できる。SQLセッションの
変数を手動で偽装するより、こちらを使う方が確実だとわかった。

### わざと壊して確認した内容

1. ポリシーを`using (id = auth.uid())`のまま → 自分の行は編集可、他人の行は編集不可（Impersonateで確認）
2. UPDATEポリシーを一時的に`using (true)`に緩める → 他人の行も編集できてしまうことを確認
3. ポリシーを`using (id = auth.uid())`に戻す → 再び他人の行は編集不可に戻ることを確認

「ポリシーを外す」ではなく「ポリシーの条件を緩める」で実験したのは、ポリシーを完全に削除すると
逆にポリシー0件＝全拒否になってしまい、意図した「無防備な状態」を再現できないため。

## M4: 二層のRLSとINSERTポリシー

### SELECTの条件をORでつなぐ

`profiles`のSELECTポリシーは`using (true)`（誰でも読める）という単純なものだったが、
`user_technologies`では「公開されているか、自分のものか」という**2つの条件のOR**が必要になる。

```sql
using ( is_public = true or profile_id = auth.uid() )
```

ここで一度`is_public = true || profile_id = auth.uid()`と書きかけたが、SQLの論理和は
`or`という単語であり、JSやCの`||`ではないことに気づいた。`||`はSQLでは**文字列連結演算子**なので、
真偽値同士に使うとエラーになる。`1=1`と`true`の話（M3参照）と同種の、他言語の感覚を
そのまま持ち込んでしまう典型パターン。

### INSERTポリシーは`with check`だけを書く

UPDATEには「対象にできる既存の行」（`using`）と「更新後の値が条件を満たすか」（`with check`）の
両方がある。INSERTには**既存の行という概念がそもそも無い**（これから作る行だけがある）ので、
`using`を書く意味が無く、`with check`だけを書く。

```sql
create policy "user_technologies_insert"
on user_technologies
for insert
with check ( profile_id = auth.uid() );
```

これにより「他人のprofile_idを詐称してINSERTする」ことをDBレベルで防げる。アプリ側のコードが
うっかり別のprofile_idを渡すバグを書いても、RLSが最後の砦として弾いてくれる。

### RLSに弾かれたUPDATE/DELETEは、エラーではなく「0件」になる

他人の行を`update`や`delete`しようとしても、権限エラーは返ってこない。文自体は成功し、
対象0件という結果になるだけ。これはM1で見た「GRANTが無い→`permission denied`という
明示的なエラー」とは対照的で、次のように整理できる。

| | 結果 |
|---|---|
| GRANTが無い（テーブルへのアクセス権自体が無い） | 明示的な`permission denied`エラー |
| RLSのポリシーで弾かれる（アクセス権はあるが、その行が条件を満たさない） | エラーにならず、静かに0件影響 |

構想と判断の記録7章にある「RLSは間違えてもエラーが出ない種類の機能」という話の実感がここにある。
ポリシーを書き間違えても画面は普通に動いてしまうので、「0件だから対象が無かった」のか
「本当は対象があるのにポリシーで弾かれている」のかは、都度きちんと確認する必要がある。

## 番外編: 共通ヘッダーを足したら全ページが動的になった話

### 何が起きたか

画面導線の見直しで`layout.tsx`に共通ヘッダー（ログイン状態を表示するナビ）を追加したところ、
`npm run build`のログでこれまで`○`（静的）だったトップページも含め、全ページが`ƒ`（動的）に
変わった。

### なぜそうなるか

M0の学習メモで触れた通り、`next build`はServer Componentのコードをビルド時に実行して
静的なHTMLを作ろうとする。ただしCookieを読む（`cookies()`を呼ぶ）ような、リクエストごとに
結果が変わる処理が含まれていると、そのページは静的化を諦めて「リクエストのたびにサーバーで
描画する」動的ページになる。

今回、共通ヘッダーは「今ログインしている人が誰か」を毎回`getClaims()`で確認する必要があるため、
Cookieを読む処理を含む。そして`layout.tsx`は**全ページ共通の外枠**なので、ヘッダーが動的になった
結果、`layout`配下の全ページが動的レンダリングに巻き込まれる。トップページ単体は元々静的で
問題無かったのに、「共通ヘッダーを足す」という一見関係なさそうな変更で静的性を失う、という
連鎖が起きた。

### 本番未設定時にどうなるか

面白いことに、本番でSupabase未設定（M6まで）の状態でビルドすると、`supabaseConfigured`ガードが
効いてヘッダーがCookieを読む処理をスキップするため、**全ページが静的に戻る**ことも確認できた。
「動的になるかどうか」は書いてあるコードそのものというより、「実行時にCookieを読む分岐を
通るかどうか」で決まる、という理解が深まった。

## 番外編: デザイン決定と実装で学んだこと

### ラジオボタンで「星評価」を作る仕組み

習熟度(1〜5)をドットで表現する`.level-picker`は、昔からある「CSSだけで星評価を作る」
テクニックをそのまま流用している。

1. ラジオボタンを**逆順**（5,4,3,2,1）に並べる
2. コンテナに`flex-direction: row-reverse`をかけると、見た目は1,2,3,4,5の順に戻る
3. `input:checked ~ label`（一般兄弟結合子）で、「チェックされた要素より**後ろにある**
   label」をすべて選択する

DOM順が5,4,3,2,1なので、例えば「3」をチェックすると、DOM上で後ろにある「3,2,1」に対応する
labelが選ばれる。それが見た目では「1,2,3」（＝チェックした値以下）に一致する。JS無しで
「選んだ値までを塗る」UIが作れるのは、こうやってDOM順と表示順をわざとズラしているから。

### Tailwind v4の`@theme`でデザイントークンを管理する

配色を決め打ちの16進色やユーティリティクラス（`zinc-50`等）で各コンポーネントに書くのではなく、
`globals.css`の`@theme inline`で`--color-bg`や`--color-accent`のような名前付きトークンとして
定義した。こうすると`bg-bg`、`text-accent`のような専用のTailwindユーティリティクラスが
自動生成される。配色を変えたくなったら`globals.css`の数行を直すだけで済み、各コンポーネントを
1つずつ書き換えなくてよい。

### 見た目の確認は`curl`では不十分

これまでの動作確認はほぼ`curl`（HTMLの中身を見る）で済んでいたが、配色やレイアウトのような
「見た目」はHTMLの構造だけでは分からない。今回はPlaywright（`npx playwright install chromium`で
ブラウザを用意し、`npm install --no-save playwright`で一時的にスクリプトから使えるようにした）で
ヘッドレスブラウザを操作し、実際にスクリーンショットを撮って確認した。

その過程で、スクリーンショット用のスクリプトで`localhost`と`127.0.0.1`のホスト名を
混在させてしまい、一瞬「プロフィールページに未ログイン扱いで弾かれる」不具合に見えた。
これはM2で学んだ「Cookieはホスト名ごとに別」という話がテストコード側で再現しただけで、
アプリ自体は正しく動いていた。見た目の検証ツールを新しく使うときも、ツール側の設定ミスと
アプリのバグを切り分ける視点は変わらず必要だと分かった。
